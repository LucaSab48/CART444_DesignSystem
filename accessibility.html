Documentation

Accessibility

Accessibility is treated as a system requirement rather than a later compliance pass. The aim is to approach WCAG 2.1 AA expectations where applicable while keeping the interface restrained, readable, and usable across keyboard, screen-reader, and low-vision contexts.

Contrast

AA

Body text should meet at least 4.5:1 contrast, while larger display text should remain at or above 3:1.

Focus

Visible

Interactive elements use a high-visibility focus ring that stays consistent across navigation, forms, and components.

Input labels

Always

Form fields use visible labels, with helper and error text placed close to the field they describe.

Principles

System expectations

Contrast expectations

  • Use dark text on the light background and white surface by default for reading content.
  • Reserve the orange accent for actions and highlights instead of long passages of text.
  • Test new combinations against WCAG 2.1 AA before adding them to the system.

Keyboard navigation

  • All controls must be reachable and operable with `Tab`, `Shift + Tab`, `Enter`, and `Space` where expected.
  • Dialogs should move focus into the modal when opened and return focus after closing.
  • Do not remove browser keyboard behavior from native controls.

Focus

Visible focus styles

Button focus

Field focus

Focus guidance

  • Focus must remain visible at all times and should not rely only on color changes inside the component.
  • Use one consistent ring treatment so the system feels coherent across controls.
  • Hover and focus should not be identical if that reduces keyboard clarity.

Semantics

HTML and labels

Semantic HTML

  • Use headings in order so screen-reader users can scan the page structure.
  • Use `
  • Use `fieldset` and `legend` for related checkboxes or radios.

Labels for form inputs

  • Do not depend on placeholder text as the only label.
  • Keep labels visible even when helper text is also present.
  • Connect helper and error messages with `aria-describedby` when they clarify the field state.
<label class="field-row">
  <span class="field-label">Email</span>
  <input class="ds-input" type="email" aria-describedby="email-help" />
  <span class="helper-text" id="email-help">Used only for project contact.</span>
</label>

ARIA

Use ARIA only where needed

Good ARIA use

  • Dialogs use role="dialog" and aria-modal="true".
  • Switches use role="switch" and aria-checked.
  • Tooltips use role="tooltip" and connect to a trigger with aria-describedby.

Avoid overusing ARIA

  • Prefer native elements before recreating behavior with custom roles.
  • Do not add ARIA if native HTML already provides the needed semantics.
  • ARIA should reinforce meaning, not patch unclear structure.

Icons

Decorative vs meaningful icons

Decorative icons

  • Hide purely decorative icons from assistive technology with aria-hidden="true".
  • Do not let visual ornament become extra screen-reader noise.

Meaningful icons

  • If an icon communicates status or function, provide text or an accessible label.
  • Do not use icon-only buttons without an accessible name.

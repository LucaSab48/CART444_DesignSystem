Component Library

Components

Components translate the foundations into repeatable interface patterns for portfolio pages, project filters, forms, and content modules. The emphasis is on restrained styling, clear interaction states, and documentation that can support reuse instead of one-off mockups.

Coverage

System goals for components

  • Every core component documents default, hover, focus, active, disabled, or error states where relevant.
  • Each pattern includes usage guidance, anatomy, accessibility notes, and starter code.
  • Component styling is tied back to shared tokens for spacing, radius, color, and focus treatment.

01

Button

Buttons trigger a single clear action. The primary orange button is used sparingly for high-priority actions, while a quieter secondary style supports cancel, view, and supporting actions.

Use it for

  • Submitting a form or confirming an action.
  • Navigating to a primary destination such as a featured project.

Avoid when

  • A text link is sufficient.
  • Several actions are competing for equal importance.

Anatomy: container, text label, optional icon, state treatment, focus ring.

Accessibility: use a real <button> for in-page actions, keep labels action-oriented, and preserve visible focus on both mouse-free and keyboard flows.

Default

Resting state with the accent fill reserved for the most important action in a region.

Hover and focus

Hover lifts slightly while focus swaps motion for a clear ring so keyboard navigation stays visible.

Active

Pressed state darkens slightly and removes the lift to communicate click confirmation.

Disabled

Use only when the action is temporarily unavailable and the reason is communicated elsewhere.

<button class="ds-button" type="button">Primary action</button>
<button class="ds-button is-secondary" type="button">Secondary action</button>

02

Text Input

Text inputs support contact forms, project metadata entry, and filter interfaces. Labels stay outside the field, helper text sits below, and error feedback appears inline.

Use it for

  • Short responses such as names, links, tags, or categories.
  • Structured form fields that need labels, validation, and helper text.

Avoid when

  • Users need to choose from fixed options.
  • The response is multi-line, which should use a textarea.

Anatomy: label, optional metadata, field container, input value, helper or error message.

Accessibility: every input needs a visible label, aria-invalid when in error, and helper text associated with aria-describedby where useful.

<label class="field-row">
  <span class="field-label">Email</span>
  <input class="ds-input is-error" type="email" aria-invalid="true" aria-describedby="email-error" />
  <span class="helper-text error" id="email-error">Enter a complete email address.</span>
</label>

03

Checkbox and Radio

Checkboxes support multi-select preferences and radios support a single required choice. Both are documented as labeled choice groups rather than standalone inputs.

Checkbox group
Radio group

Show an error only when a required selection has not been made.

Use it for

  • Checkboxes for multiple independent selections.
  • Radios for one mutually exclusive answer.

Avoid when

  • The option count is long enough to require filtering or search.
  • A binary preference would be clearer as a toggle.

Anatomy: group label, control, text label, optional helper or error message.

Accessibility: keep the touch target on the label, group related radios with <fieldset> or role="radiogroup", and never rely on color alone to show checked or invalid state.

<label class="choice-row">
  <input type="radio" name="project-type" />
  <span>Featured project</span>
</label>

04

Toggle / Switch

Toggles represent an immediate on or off setting, such as enabling captions or revealing additional metadata.

Default
Hover
Focus
On
Disabled

Use it for

  • Binary settings that take effect immediately.
  • Preferences that benefit from seeing on and off states at a glance.

Avoid when

  • The user must confirm the action later with a submit button.
  • The choice is not truly binary.

Anatomy: switch track, thumb, state label, and accessible name.

Accessibility: use role="switch" with aria-checked, ensure the label explains the setting, and do not use the toggle alone to communicate critical status changes.

<button class="ds-switch" type="button" role="switch" aria-checked="false" aria-label="Enable captions"></button>

05

Dropdown

Dropdowns reduce visual clutter when users need to choose one option from a short predefined set such as project type or display order.

Use it for

  • Short lists with one clearly selected option.
  • Cases where a text input would introduce unnecessary ambiguity.

Avoid when

  • Users need to compare all options at once.
  • The list is long enough to require search or grouping.

Anatomy: label, selected value, indicator, list of options, helper or error text.

Accessibility: a native <select> keeps keyboard support and screen-reader semantics without extra scripting, which is the best fit for this system.

<label class="field-row">
  <span class="field-label">Category</span>
  <select class="ds-select">
    <option>Film</option>
  </select>
</label>

07

Alert

Alerts communicate status without taking users out of the current flow. They are useful for submission feedback, publishing state, or system notices.

Draft saved

Your notes have been stored locally.

Project published

The case study is now visible in the archive.

Metadata incomplete

Add a project category before exporting.

Submission failed

Check the required fields and try again.

Use it for

  • Short, contextual updates that need immediate visibility.
  • Success, information, warning, or error messaging near the related action.

Avoid when

  • A blocking confirmation requires explicit user choice.
  • The message is decorative rather than actionable.

Anatomy: tone, title, supporting message, optional dismiss action.

Accessibility: use role="status" for passive updates and role="alert" for urgent errors that should be announced immediately.

<div class="ds-alert error" role="alert">
  <div>
    <strong>Submission failed</strong>
    <p>Check the required fields and try again.</p>
  </div>
</div>

08

Tooltip

Tooltips provide brief clarification for controls with non-obvious labels. They should support, not replace, visible labels.

Use collections to group related work without changing project categories.

Hover or focus the button to reveal the tooltip.

Use it for

  • Short clarifications that help interpret a label or icon.
  • Supplemental guidance that is useful but not required for task completion.

Avoid when

  • The content is essential instruction or validation feedback.
  • The message is longer than a short sentence.

Anatomy: trigger, tooltip bubble, arrow, helper text relationship.

Accessibility: tooltip content must also be available to keyboard users, and critical information should remain visible in the layout instead of hidden behind hover.

<button aria-describedby="tooltip-id" data-tooltip-target="tooltip-id">Collections label</button>
<div id="tooltip-id" role="tooltip" hidden>Short clarification.</div>

09

Progress

Progress indicators communicate completion through a simple bar and text label. They work well for uploads, longer forms, or staged publishing.

Portfolio setup 72%

Always pair the bar with a text value or status label.

Use it for

  • Task progress that changes over time.
  • Multi-step flows where users benefit from knowing how much remains.

Avoid when

  • The action is effectively instant.
  • The system cannot estimate completion meaningfully.

Anatomy: label, percentage or status text, track, fill.

Accessibility: expose the numeric value with aria-valuenow and do not rely on color alone to convey completion.

<div class="progress-track" role="progressbar" aria-valuemin="0" aria-valuemax="100" aria-valuenow="72">
  <div class="progress-bar" style="width: 72%;"></div>
</div>

10

Dialog / Modal

Dialogs interrupt the current flow to request confirmation or present a focused decision. They should be used sparingly and reserved for tasks that cannot be handled inline.

Confirmation

Publish project update?

This will replace the current portfolio summary and make the new version visible immediately.

Use it for

  • High-impact confirmations, destructive actions, or brief focused tasks.
  • Moments where background content should be temporarily paused.

Avoid when

  • The task can be completed inline with less interruption.
  • The content becomes long, scroll-heavy, or multi-step.

Anatomy: scrim, dialog container, title, message, primary action, dismiss action.

Accessibility: identify the dialog with role="dialog" and aria-modal="true", move focus into it when opened, and provide a reliable close action.

<div class="ds-dialog" role="dialog" aria-modal="true" aria-labelledby="dialog-title">
  <h3 id="dialog-title">Publish project update?</h3>
  <button type="button">Publish</button>
  <button type="button">Cancel</button>
</div>

Use for video or motion-heavy projects.

Form guidance

  • Use visible labels instead of placeholder-only fields.
  • Place helper text below the field and errors adjacent to the problem.
  • Keep required inputs minimal so the form feels manageable.

Accessibility

  • Use native fieldset and legend for grouped controls.
  • Associate errors with the input using aria-describedby and aria-invalid.
  • Preserve keyboard access to all controls, including switches and submit actions.
<fieldset class="control-stack">
  <legend class="control-label">Presentation type</legend>
  <label class="choice-row">
    <input type="radio" name="presentation-type" />
    <span>Thumbnail card</span>
  </label>
</fieldset>
